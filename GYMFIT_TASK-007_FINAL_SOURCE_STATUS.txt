Order status flow
- PENDING -> CONFIRMED or CANCELLED.
- CONFIRMED -> PROCESSING or CANCELLED.
- PROCESSING -> SHIPPED or CANCELLED.
- SHIPPED -> DELIVERED.
- DELIVERED and CANCELLED are terminal.
- PENDING -> CONFIRMED requires PAID.
- PAID must be REFUNDED before cancellation; PENDING payment and PARTIALLY_REFUNDED cannot be cancelled.

Payment status flow
- Customer: UNPAID -> PENDING; repeat notification while PENDING is idempotent.
- Admin: PENDING -> PAID or FAILED; FAILED -> UNPAID; UNPAID -> PAID; PAID -> REFUNDED.
- Same-status and unsupported transitions return business conflicts.
- Direct FAILED -> PENDING is not allowed.

Reservation lifecycle
- Create order increases reserved without changing on_hand.
- UNPAID expiration, customer cancellation, and valid admin cancellation release reserved only.
- CONFIRMED, PROCESSING, and SHIPPED do not change inventory.
- DELIVERED decreases both reserved and on_hand and records InventoryAdjustment.
- Payment PENDING/PAID and terminal orders have no active expiration.
- FAILED -> UNPAID creates a new expiration deadline.

Refund lifecycle
- Refund is an admin-only manual record transition from PAID to REFUNDED.
- Refund note is required.
- No Stripe or bank API is called.
- Payment history is committed with the payment update; email is attempted only after commit.
- Order cancellation becomes valid only after the payment status is REFUNDED.

Cart/Checkout flow
- Canonical cart item is { productId, variantId, quantity }.
- Cart identity is productId plus variantId; the same variant is merged and different variants remain separate.
- Legacy product-only cart entries resolve a display variant once during migration.
- Cart stores identity and quantity only; current price and availability are reloaded from the product API.
- Checkout preserves the selected variantId end to end and clears cart only after successful order creation.

Customer Order flow
- POST, list, detail, cancellation, and payment-notification routes require JWT authentication.
- Customer detail, cancellation, and payment notification enforce the authenticated owner.
- /orders and /orders/:orderId are protected frontend routes with list/detail navigation.
- Customer list is paginated, newest-first by default, owner-filtered, and does not expose admin history.

Admin Order flow
- Admin list/detail/status/payment endpoints require backend ADMIN authorization.
- Frontend and backend order/payment transition options are aligned.
- Payment and order histories are exposed to Admin detail only.
- Legacy Product Order Stripe response/search fields were removed from the active admin contract.

Gmail configuration requirements
- MAIL_HOST, MAIL_PORT, MAIL_SECURE, MAIL_USER, MAIL_APP_PASSWORD, and ADMIN_NOTIFICATION_EMAIL are required.
- MAIL_PORT must be 1-65535 and MAIL_SECURE must be exactly true or false.
- Product Order MAIL_* configuration is separate from legacy membership SMTP_* configuration.
- Missing configuration and delivery failure are distinct results.
- Database commits are not rolled back by mail configuration or delivery failures.

Bank configuration requirements
- BANK_NAME, BANK_ACCOUNT_NAME, BANK_ACCOUNT_NUMBER, and BANK_QR_IMAGE_URL are required.
- QR accepts a local relative path beginning with one slash or a valid HTTPS URL.
- Windows paths, protocol-relative URLs, file:, javascript:, data:, malformed HTTPS, and other schemes are rejected.
- Incomplete configuration blocks customer payment notification with 503 before mutation and hides the notification action in customer UI.
